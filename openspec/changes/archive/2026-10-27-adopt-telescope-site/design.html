Goals and non-goals

Keep one shared implementation for site mechanics. Make the first consumer build reproducible from published artifacts, preserve the existing URLs, and keep diagram semantics in their current library modules. Use this site as a real integration consumer for Telescope.

This design does not add a diagram renderer to Telescope, move project examples into Telescope, require a runtime service, or standardize Smithy and Morphir workbenches. The scope exclusions are in the proposal.

Decisions

DEP-1. Owner: consume a released Telescope

The consumer migration depends on Telescope's extract-project-site-toolkit change and its owner-approved publication. Pin the published library and CLI versions. A clean checkout must resolve them without the sibling clone, path overrides or a branch ref. Do not guess an initial version in this proposal. Use the release's documented compatibility tuple when the library and CLI have different module names.

A local workspace override would make extraction easier to try but would not prove the requested released consumer. It can be used only in a temporary Telescope integration fixture before publication, never as this repository's landed site dependency.

OWN-1. Call: keep a small consumer adapter

Retain apps/site as an unpublished adapter for project configuration, trusted page extensions and example providers. Move reusable parsing, shell, search, navigation and asset checks to Telescope. Prefer the published API to a copied generator fork. Keep scripts/site.mbtx as the command boundary so existing mise tasks and CI can call the same build/check/test/preview interfaces.

Generic moon doc ingestion and version-tree handling must be available through released optional adapters or a small local compatibility adapter before migration. A local adapter may translate project metadata or assemble existing artifacts; it must not duplicate a shared content parser, theme or route engine.

GAL-1. Call: export a checked example manifest

Extend the existing gallery exporter to write versioned metadata for selected qualified examples. Each entry has a stable ID, title, family, source format, supported scope and description; paths for sources and SVG previews; and optional player artifacts with an illustration, exploration or supplied-evidence label. The manifest schema and typed conversion must match the released Telescope gallery contract.

Resolve paths under a single allowed artifact root, reject traversal and escaped symlinks, check duplicate IDs and required files, then pass the checked artifacts to Telescope. Reuse the SVG/player bytes that the renderer pipeline already qualified. Do not render from source a second time inside Telescope.

The index groups examples by family. Stable detail pages show the source, preview, downloads and an optional link to the standalone player. Linking the player avoids loading its scripts on every gallery or docs page. Static previews and links remain usable without JavaScript.

UI-1. Call: update the landing page and add gallery navigation

Use project-owned content and Telescope components to explain sequence, BPMN, swimlane, regex, EBNF, JSON and YAML support. A representative preview links to the gallery; documentation and getting-started links remain prominent. Each gallery detail page states its supported scope. A source-format label must not imply support for every diagram in that format.

Use adaptive or checked light/dark SVG previews. Preserve keyboard focus, mobile navigation and the existing reduced-motion behavior in players. Keep source examples selectable and downloadable.

URL-1. Call: preserve routes and historical artifacts

Keep /diagrams.mbt/, the next tree, minor-release trees, latest, versions.json, banners and canonical links. Capture a route-and-anchor baseline before removing local engine code. Compare docs, API, articles, feeds and asset references against that baseline. Previously released site archives remain valid input; never require rebuilding old tags with Telescope.

A new site without API pages or historical release assembly would be easier to build but would break the current publishing contract. A gallery is an added route family, not a replacement for those pages.

DOC-1. Owner: HTML designs with local assets

New changes use html-design. The document template and local highlight assets come from Morphir with their license and upstream records. This repository stores the template in .agents/templates/ because its current content scanner publishes HTML below docs/. Keep existing changes on their declared schemas, and repair relative asset paths when archiving.

Migration plan

  1. After plan approval, create one epic and story per task group. Record the Telescope release dependency.
  2. Wait for an owner-approved Telescope publication. Build one thin landing/docs/gallery path using its real release in an independent checkout.
  3. Replace the remaining shared site code, retain compatible API/version behavior, and remove copied mechanics only after the compatibility checks pass.
  4. Export gallery artifacts for each implemented family and update the landing page and navigation. Keep each group's tests and docs with its implementation.
  5. Run the full repository checks and the site build, link and browser suites. Deploy through the existing GitHub Actions flow after review and merge.

Rollback is a revert of the consumer migration to the prior local engine and pinned inputs. Keep historical site release assets unchanged. No library release is required solely to publish this site migration.
