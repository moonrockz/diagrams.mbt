Context

The stable MoonBit FFI and package pages say that the native backend cannot export a foreign_library package as a linkable artifact, such as a .so or .dll. We examined the pinned toolchain (moon 0.1.20261021, moonc v0.10.17+093cb8f9c) before we made a decision. These are the results of a probe module:

  • A native foreign_library package builds into a static archive, <package>.a. There is no shared library and no main.
  • In release mode, moonc link-core writes C (the C backend). Then cc -c compiles it, and libtool -static puts it into the archive with the precompiled mimalloc object and the runtime objects. Debug mode uses the new native backend, which writes an object file directly.
  • Each #export_name function becomes a plain C wrapper. The generated C also defines void moonbit_init(void). It calls moonbit_runtime_init(0, 0), sets the layout table and initializes the top-level values. The pinned moonbit.h declares moonbit_init for hosts of a compiled library. The header calls itself a "very unstable API".
  • An export borrows its Bytes argument (measured; see OWN-1).
  • The bundled mimalloc does not define malloc or free, so it does not replace the host allocator. moonbit_panic calls abort().

Thus the gap in the documentation is a shared library, not a static archive. A CPython extension is a shared library that we link ourselves, so the archive is sufficient as input.

Goals and non-goals

Goals: prove a CPython import that calls the existing Mermaid-to-SVG code in the same process. Give structured diagnostics and output that equals the direct MoonBit output. Record initialization, ownership, sanitizer results and repeated-call measurements, and make the build repeatable.

Non-goals: the items under "Out of Scope" in the proposal.

Decisions

LINK-1. Call: link the archive of a native foreign library

The package apps/python-native/ffi has the kind foreign_library and supports only native. Moon builds it in release mode with the C backend. The build task links the resulting archive and a small C adapter into a CPython extension module. The task does not copy or patch the generated C.

Alternative: compile the generated .c file and the runtime sources directly. This gives full control of compiler flags, so the sanitizer build uses it. It depends on file names inside _build, so it is not the default. Rejected alternatives: a subprocess wrapper and a WebAssembly build. They do not answer the question.

ABI-1. Call: one versioned bytes-in, bytes-out entry point

The library exports two symbols with prefix diagrams_py_:

  • int32_t diagrams_py_abi_version(void)
  • moonbit_bytes_t diagrams_py_render_svg(moonbit_bytes_t utf8_source)

The FFI page gives Bytes a stable mapping to uint8_t*. The result is UTF-8 JSON with a format version, the media type, the optional output and the diagnostics. Only the adapter and the MoonBit bridge know this format. Python code does not see MoonBit structs, enums, strings or mangled names. The adapter checks the version when the module loads and refuses a mismatch with ImportError.

Alternatives: opaque result handles with accessor functions, or C structs. They need more exported symbols and expose more of the runtime layout. JSON costs one extra copy of the SVG, which is acceptable for a spike.

OWN-1. Call: copy at the boundary and release each value one time

The FFI page describes an owned convention for extern "C" declarations, but it does not state the convention for #export_name functions. A C probe on the pinned compiler showed that the export borrows its Bytes argument and returns a new reference. The first adapter assumed the owned convention and leaked each input; the leaks tool found it. The adapter now:

  1. gets the UTF-8 buffer of the Python string. The string owns this buffer.
  2. allocates a MoonBit Bytes value with moonbit_make_bytes_raw, copies the buffer into it and calls the export.
  3. releases the argument with moonbit_decref, copies the returned Bytes into a new Python object and releases the result.

No MoonBit pointer stays in Python after a call. A Python object never points into MoonBit memory. A change of the convention shows as a double free in the sanitizer build or as allocator growth in the measurement task.

INIT-1. Call: initialize one time and never tear down

The module execution slot calls moonbit_init one time for each process, protected by a static flag. MoonBit has no shutdown function, so the runtime and its top-level values stay until the process stops. The module uses multi-phase initialization and declares Py_MOD_MULTIPLE_INTERPRETERS_NOT_SUPPORTED.

GIL-1. Call: hold the GIL and serialize calls

The runtime has process-global state, for example the cycle collector root buffer. The adapter does not release the GIL during a render, so calls are serialized. The spike makes no claim about threads, free-threaded builds or subinterpreters.

API-1. Call: Limited API 3.12 for the adapter

The adapter uses only Limited API functions and defines Py_LIMITED_API=0x030C0000. The build writes an .abi3.so file, and the tests load the same file in two pinned CPython versions. This is evidence for later packaging. It is not a wheel.

TEST-1. Call: compare with an independent native oracle

A native MoonBit executable calls render_svg directly for each fixture file. It writes the SVG and one line for each diagnostic. It does not use the bridge JSON. The Python tests compare their results with these files and also run repeated mixed calls.

AUTO-1. Call: build automation in an .mbtx task

scripts/python-native.mbtx uses moonbitlang/async processes to run moon, cc and Python. mise tasks select a pinned CPython for these tasks only. mise run check builds and tests the MoonBit packages on all targets, but it does not need Python.

Risks and trade-offs

RiskMitigation
A MoonBit panic calls abort() and stops the Python process.Report it. Use renderer limits and diagnostics. A production design needs a panic policy from upstream or a process boundary.
moonbit.h, moonbit_init, archive contents and the export convention are unstable or undocumented.The adapter uses one generated and three runtime symbols, plus one header macro. It checks a boundary version. The toolchain stays pinned.
Moon compiles the archive objects without -fPIC. Linux shared objects can need it.macOS arm64 code is position-independent. Record the Linux risk and the direct-compile alternative.
Two extensions that each link a MoonBit runtime can conflict.Export only PyInit__diagrams_native. Record it as a deployment risk.
Flat RSS does not prove that there is no leak.Use sanitizers, allocator counts and leak tools where they are available. Report the limits.

Open questions

  • Will upstream MoonBit support a shared native library, a panic hook or a runtime shutdown function?
  • Must a production package use one process-wide runtime for each wheel, or one shared runtime for all MoonBit extensions?
